2. Missing Lifecycle Cascades

- MAR reconciliation still runs without requiring a canonical signed physician order at the call boundary. The service passes `p_preferred_physician_order_id: null`, and the shared RPC still contains its own anchor-selection logic. That leaves the `signed POF -> MAR` dependency softer than it should be. See [`/D:/Memory Lane App/lib/services/mar-reconcile.ts`](/D:/Memory Lane App/lib/services/mar-reconcile.ts:37) and [`/D:/Memory Lane App/supabase/migrations/0056_shared_rpc_orchestration_hardening.sql`](/D:/Memory Lane App/supabase/migrations/0056_shared_rpc_orchestration_hardening.sql:603).
- A physician order can be signed while downstream MHP/MCC/MAR sync is still incomplete. The service explicitly returns `postSignStatus: "queued"` and tells downstream consumers not to treat the order as operationally ready yet. That means the canonical lifecycle is still `sign now, repair by queue if needed` instead of `sign only when downstream sync is durably complete`. See [`/D:/Memory Lane App/lib/services/physician-order-post-sign-service.ts`](/D:/Memory Lane App/lib/services/physician-order-post-sign-service.ts:24) and [`/D:/Memory Lane App/lib/services/physician-order-post-sign-service.ts`](/D:/Memory Lane App/lib/services/physician-order-post-sign-service.ts:212).
- Signed-POF retry sync still rebuilds MHP diagnoses, medications, and allergies by deleting and re-inserting member-clinical rows from the signed POF snapshot. If retries run after staff has already made newer downstream edits, the stale signed-order snapshot can overwrite them. See [`/D:/Memory Lane App/supabase/migrations/0205_fix_signed_pof_sync_member_id_ambiguity.sql`](/D:/Memory Lane App/supabase/migrations/0205_fix_signed_pof_sync_member_id_ambiguity.sql:148).
- Enrollment packet `completed` / `filed` still depends on repair-style follow-up for operational shells, completed-packet artifact linkage, and lead activity. The completion cascade actively checks for missing MHP, MCC, attendance, member-file linkage, and mapping status after the packet is already in a completed state. See [`/D:/Memory Lane App/lib/services/enrollment-packet-completion-cascade.ts`](/D:/Memory Lane App/lib/services/enrollment-packet-completion-cascade.ts:338) and [`/D:/Memory Lane App/lib/services/enrollment-packet-completion-cascade.ts`](/D:/Memory Lane App/lib/services/enrollment-packet-completion-cascade.ts:516).
- Enrollment packet readiness remains a softer status model instead of a hard lifecycle truth. The system distinguishes `completed`, `filed_pending_mapping`, `queued_degraded`, and `operationally_ready`, which is better than pretending everything is done, but it also confirms that completion does not equal downstream readiness. See [`/D:/Memory Lane App/lib/services/enrollment-packet-readiness.ts`](/D:/Memory Lane App/lib/services/enrollment-packet-readiness.ts:46) and [`/D:/Memory Lane App/lib/services/enrollment-packets-public-runtime-context.ts`](/D:/Memory Lane App/lib/services/enrollment-packets-public-runtime-context.ts:228).
- Signed intake assessments can still finish with queued follow-up for draft POF creation or member-file PDF persistence. That means intake signature truth is persisted before the downstream intake -> POF -> member files chain is guaranteed complete. See [`/D:/Memory Lane App/lib/services/intake-pof-mhp-cascade.ts`](/D:/Memory Lane App/lib/services/intake-pof-mhp-cascade.ts:391).

6. Suggested Fix Prompts

- Add composite lineage FKs for the remaining clinical chain. Create a forward-only Supabase migration that preflights and fails on mismatched rows, then adds and validates:
  `physician_orders (intake_assessment_id, member_id) -> intake_assessments (id, member_id)`,
  `member_health_profiles (active_physician_order_id, member_id) -> physician_orders (id, member_id)`,
  `member_command_centers (source_assessment_id, member_id) -> intake_assessments (id, member_id)`,
  `pof_requests (physician_order_id, member_id) -> physician_orders (id, member_id)`,
  and composite `(care_plan_id, member_id)` FKs for care-plan signature/event tables.

- Remove queue-only truth from signed POF readiness. Refactor the signed-POF post-sign workflow so provider signature success does not imply operational readiness. Add a canonical readiness field on `physician_orders`, have the shared RPC own it, and make read models treat `signed + not ready` as incomplete. Prevent retry sync from overwriting newer downstream clinical edits unless the source version still matches.

- Tighten enrollment packet completion truth. Add a canonical completion/readiness contract so `completed` or `filed` is not treated as fully done unless completed-packet artifact linkage, downstream mapping, and required operational shells are present. Keep repair tooling for legacy recovery, but stop using completion status alone as the workflow truth.

- Harden care-plan and MAR terminal-state enforcement. Add a canonical transition guard so `care_plans.status = 'Completed'` requires `nurse_signature_status = 'signed'` and `post_sign_readiness_status = 'ready'`, and add MAR-side write guards that reject administrations against inactive or ended medication/schedule rows.

- Tighten intake lead/member identity integrity. Add a service-layer guard and, if the schema can support it cleanly, a migration-backed relational contract that rejects `intake_assessments` rows whose `lead_id` does not match the member’s canonical lead lineage.

7. Founder Summary

The repo is in better shape on classic orphan protection than it was earlier in the year. The core member, intake, POF, medication, and MAR tables now have meaningful FK coverage, and the specific failure modes “intake references nonexistent member,” “MAR references nonexistent medication,” “care plan references nonexistent diagnosis,” and “enrollment packet completed without member creation” are not the main production risk today.

The real remaining risk is softer than that: several important workflows still record upstream success first and rely on follow-up queues or repair passes to finish downstream truth. The biggest examples are signed POF readiness, enrollment packet completion readiness, and intake post-sign follow-up. That means staff can end up with records that are technically committed but not yet operationally safe to trust end-to-end.

Safest next step: add the missing composite lineage constraints first, then tighten readiness/state coupling for signed POF, care plan completion, and enrollment packet completion so downstream consumers stop treating queued follow-up work as finished truth.
