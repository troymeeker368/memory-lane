Basis: repo and migration audit only. I did not verify the live Supabase project's deployed policies, grants, PostgREST RPC exposure, or storage rules.

## 1. Executive Summary
- The most serious open risk is still at the database boundary, not the UI. Several `SECURITY DEFINER` RPCs are still executable by `authenticated`, which means a signed-in user could bypass app-layer checks if they can call Supabase RPCs directly.
- Broad legacy read policies still expose cross-member data in intake, photos, member support tables, care-plan events, and enrollment-packet internal workflow tables.
- The public enrollment packet flow is safer than it was earlier this month: the expired-parent-token completed-download bug is fixed in code. The remaining public-flow issue is mainly throttling and abuse resistance, especially for enrollment packets, POF signing, and care-plan signing.
- I did not find a browser/client exposure of `SUPABASE_SERVICE_ROLE_KEY`. Service-role use remains server-only, but one privileged overfetch path is still open in Member Command Center detail loading.

## 8. Recommended Security Hardening Plan
1. Revoke `authenticated` execute on the high-risk `SECURITY DEFINER` RPCs first: `rpc_delete_member_file_record`, `rpc_prepare_care_plan_caregiver_request`, `rpc_transition_enrollment_packet_delivery_state`, `rpc_void_enrollment_packet_request`, `rpc_finalize_enrollment_packet_submission`, and the public signature finalization RPCs. Move them to `service_role` only, or enforce `auth.uid()` and permission checks inside the function body.
2. Tighten the broad read policies next on intake, member photos, member support tables, care-plan events/diagnoses, enrollment packet internal tables, and pricing reads.
3. Remove the Member Command Center privileged overfetch path so non-clinical viewers never hydrate clinical `member_files` rows before filtering.
4. Move public enrollment-packet throttling into an atomic RPC or claim-based database path, then add comparable throttling to public POF and care-plan signature endpoints.
5. Add RLS to `sites`, `lookup_lists`, and `punches_linked_time_punch_review`, then verify the live project has the same grants and policies deployed.
